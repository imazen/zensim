## The zen-metrics CLI bug

`zen-metrics batch --metric zensim` invokes `Zensim::new(ZensimProfile::latest())`. Per
`zensim/src/profile.rs:48-50`, `latest()` returns
`Self::PreviewV0_2`. That's the **linear-weights** path (228 features
dot weights), not the trained MLP path. So the metric column emitted
by zen-metrics CLI's `zensim` is V0_2's distance, not V0_X's.

**Implications for the comparison-site**:

- `cid22.parquet`'s `score_zensim` column from this backfill chain is
  V0_2 output. The earlier "V0_16 vs fast-ssim2 -0.022 loss" finding
  WAS A V0_2 result — V0_2 truly does trail fast-ssim2 by ~0.022.
  V0_16 ≠ V0_2 ≠ that result.

- The site's JS-MLP path (mlp.js + `weights/v0_16.bin`) applied to
  feature vectors from a parquet WOULD produce the true V0_16 output.
  But the unified parquets carry the V0_2 / sweep-time zensim score
  in their `score_zensim` column, not V0_16. (The JS-MLP path needs
  to be hit explicitly via the Y-axis dropdown when feat_* columns
  are available.)

- The fix is either:
  1. Re-export `cid22.parquet` (and AIC parquets) using a CID22-
     scoring path that uses the V0_4 profile.
     `dataset_metric_baseline` already does this; we'd need a TSV
     export from it.
  2. Add a `--profile preview-v0-4` flag to zen-metrics CLI so
     `batch --metric zensim --profile preview-v0-4` produces V0_16.
     Better long-term fix; needs a zenmetrics PR.
