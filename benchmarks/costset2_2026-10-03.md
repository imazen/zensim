## Limits first
* **The prepared map's biggest fixed cost is NOT removed.** For every v2-bearing plan the prepared session runs the v1 attribution walk a second time
  (`fused_basic_into_at_revision` with no reusable basic walk): 57-59 ms at 1 MP against 8.8 ms when the scalar walk's basic planes are reused (basic-only plans).
  Reusing the fold's data would change the basic map's coefficient derivation bit for bit (different accumulation order), which the brief's "maps bit-identical" gate forbids;
  removing it bit-identically needs a v2 walk that can switch the v1 block off (`ComputeSet.v1_basic` is hard-set on). Not attempted; a decision for the coordinator.
* **Omitted v2 scales were already skipped by the prepared pass B** (it skips every (scale, channel) cell with zero sensitivity; measured pass B 0.5 ms with v2 scale 3 only,
  11 ms for scales 1-3, 40.6 ms for all four, before this change). What looked like "map cost does not fall with omitted scales" was the second v1 walk, a constant.
* Timing is a loaded-box measurement: load average 18-27 on 32 threads during the runs (fleet workers on the other cores), zenbench flagged all four runs UNRELIABLE
  (resource-gate waits), 25 rounds per size, CPU 8, single thread. Ratios inside one interleaved run are the evidence; absolute milliseconds are not comparable with earlier days.
* Rev4 rows use the Rev3-trained weights stamped as revision 4 (`bake_stamp_revision`): they price the Rev4 served path, not Rev4 model quality. REV4VEC is vectorising the canonical leaves concurrently,
  so the Rev4 absolute numbers will move. **These Rev4 timings were taken on the tree before REV4VEC's vectorised leaves landed (main 8403d272 now carries them); the bookmark was rebased onto that main afterwards and only the all-features lib suite was re-run.**
* A new unit test was observed to fail on the intermediate planner (mask not engaged); it was not re-run against the exact parent commit.
* Release-mode tests only (the CI feature cells normally run debug): the known debug-only failure `rev4_tailhist_quantile_semantics` is outside this change.

## Two findings that matter more than the mask
1. **Identity-layout (944-wide) bakes pay for blocks they never read.** The planner turns on a block's compute when the declared WIDTH reaches it ("layout-only flags are not built"),
   so every bake trained on the 944-wide table (all COSTSET bakes) computed append/append2/CSFW although no ID >= 720 is read, and that blocked every channel optimisation.
   The `densify` owner (`bake_dial_refit densify`, 512-row bit-identity gate, passes) removes it: same-run comparison at Rev3, 1 MP scalar / prepared: v2basic 86.5 / 235.7 ms dense vs
   105.1 / 255.4 identity; by_v2s123 35.1 / 107.7 vs 40.9 / 115.6; basic228 38.0 / 91.3 vs 37.9 / 92.8 (nothing to skip). The same applies to the REV4SERVE featpot v2+basic bake, whose measured
   582 ms (Rev3, 1 MP) is a 1825-wide identity layout; a dense twin should cost a fraction of that. **Densify before serving or costing any wide-trained bake.**
2. **With a dense layout the new channel mask makes the fine-Y set cheap:** `by_v2fy` (basic with X/B only at scales >= 1, v2 Y at scale 0 and all channels at scales 1-3):
   scalar 45.3 ms vs v2basic 82.2 ms (0.55x), prepared 120.0 vs 209.9 ms (0.57x) at 1 MP; 4 MP 197.4 vs 369.0 and 509.6 vs 908.7. The same IDs on the identity-944 bake cost 99.1 / 181.3 ms.
   Its COSTSET quality: human eval SROCC 0.9304 vs 0.9314, MAE 8.356 vs 8.201 (inside seed spread), broad 85/96 vs 88, owner 12/12 vs 10/12.
   `b156_v2yall` (Y-only v2 beside full basic) saves nothing in the walk (82.3 ms): full basic reads X/B at every scale, so no chroma work can be skipped.
   **by_v2fy is the best answer so far to "cheaper and as good as v2 + basic"**; its ID list is in `costset2_2026-10-03.candidate_ids.json` (not in the E12 queue; add it).

## What changed (code)
* `feature_plan.rs`: for a request that reads only f0-227 and f372-719 with the v2 block running, the plan now (a) derives the X/B work it can skip - chroma is kept at a scale only if some wanted
  slot has channel X or B there (`edge_width_change` also keeps scale+1) and the requests' other families are channel-local; (b) turns the free-extras accumulation off (its only touched
  class-C slots are the v2 `MSE` slots, which the running v2 kernel finalizes itself). `normalized` keeps the coarse-chroma mask when only channel-local families run.
* `feature_v2.rs`: `ComputeSet::chroma_local_families()`; `allows_full_res_y_subset` accepts v2 scale 0 when no cross-channel family runs. The walk's existing `ALL_CHANNELS=false` path does the skipping; no kernel changed.
* Test `v2_plans_skip_unread_chroma_work_without_changing_any_feature`: six ID sets (basic Y + v2 Y, fine-Y combinations, peaks Y, chroma edge-width, and negatives: full basic + Y-only v2, full v2 + basic, an append read)
  - mask engaged exactly when expected, `edge_width_change` keeps scale+1, and every consumed feature is bit-identical to the unrestricted extraction at 64x64, 97x65 and 128x96.
