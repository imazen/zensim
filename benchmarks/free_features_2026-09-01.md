# Free features — what the 156 walk can carry for nothing, and what it actually costs

Continues `51565aa5` (`V1FreeExtras::RawMoments`), which added the accumulator
but deferred its A/B. Companion: `benchmarks/feature_cost_frontier_2026-08-31.md`
(the model-class frontier this lane's classification extends downward, into
the 156-only walk specifically).

**The question:** given a production walk that computes only the v1-basic 156
columns (`f0..156`), how many of the other 788 slots in the 944-wide table can
ride along for zero (or near-zero) marginal cost, and does having them change
any model's answer?

---

## 1. Classification — all 944 slots, by marginal cost given the 156 walk

Read from source (`zensim/src/fused.rs`, `zensim/src/feature_v2.rs`), not
assumed. Generator: `scripts/freefeats_classify.py`; output:
`benchmarks/free_features_2026-09-01/slot_classification.tsv` (944 rows + 1
header, one row per slot). The TSV is **regenerated byte-for-byte** by the
script — verified (`diff -q` clean) before landing, so the table is not
hand-maintained drift waiting to happen.

Taxonomy (the brief's five classes, split three ways where source forced it):

| class | meaning | slots |
|---|---|--:|
| `computed` | the 156 walk **is** this — always on | 156 |
| `A` | already-computed, EMIT-ONLY (peaks: unconditional in every SIMD variant of `fused_vblur_ssim_inner*`) | 72 |
| `A0` | structurally CONSTANT (correct-zero) on this route | 39 |
| `B` | finalize-only from sums the 156 walk *already* keeps unconditionally | 0 |
| `C-raw` | in-register cheap, reads only `s`/`d` — value equals the 944 table's value | 49 |
| `C-blur` | in-register cheap, reads V-blurred `mu1/mu2/ssq/s12` too — computable free but **NOT the same feature** (a v1 band re-inits its V-blur recurrence at the band buffer top; phase A runs it over the whole strip window) | 154 |
| `C-xch` | reads a plane from another channel (`ref_y`) — no new compute, new stream | 33 |
| `D` | needs a plane the 156 walk does not make (`activity`, `bs2`, `act_x/b`) | 359 |
| `E` | needs its own pass (gradient stencil, blockiness lattice) | 82 |
| **TOTAL** | | **944** |

Sums to 944 (asserted by the generator). `B` has **zero occupants**: every
candidate for "finalize-only from sums the 156 walk already keeps" turned out
to need either an unconditional existing accumulator (→ `A`) or a new
accumulator over already-live registers (→ `C`) — an empirical finding about
what's in source, not a taxonomy defect.

**The free set** (script's own definition: `A` + `C-raw`, excluding v2's
`MSE` — same reads-only-`s`/`d` shape but division-bearing, i.e. it needs a
scalar divide by a *different* N than the v1 walk's, so it is not a pure
register-carry): **109 slots — 72 peaks (already shipped, `V1PoolsMode::Peaks`)
+ 37 raw-moment** (the 40 slots `51565aa5`'s accumulator touches, minus 3 that
fall under the unrelated `APPEND_SKIP_B_SCALE0` zero-override and are counted
under `A0` instead, not double-counted). Both "40" and "37" are correct for
what they measure; this note exists so a reader doesn't take them as
disagreeing.

Raw-moment slot indices (944-layout, i.e. `feat_<n>`):
`733,734,735,750,751,752,784,785,786,801,802,803,818,819,820,835,836,837,
852,853,854,869,870,871,886,887,888,903,904,905,920,921,922,926,931,936,941`
— the `GLOBAL_DMEAN`/`GLOBAL_CGAIN`/`GLOBAL_CLOSS` triple per (scale, channel)
in the append-204 block (minus the scale0/ch2 override) plus `LUMA_MEAN_REF`
per scale in append2.

Reproduce: `python3 scripts/freefeats_classify.py /tmp/check.tsv && diff /tmp/check.tsv benchmarks/free_features_2026-09-01/slot_classification.tsv`.

## 2. Cost — does the free superset walk actually cost nothing?

**Implementation.** `zensim/src/fused.rs`'s `raw_moments` accumulation (6
vector SIMD sites + 4 scalar-tail sites, matching the 10 accumulation sites
`51565aa5` added) now vector-adds each row into per-lane accumulators
(`fm_s`/`fm_d`/`fm_s2`/`fm_d2`) and `reduce_add()`s **once**, at the band's
last inner row — not `reduce_add()` (a horizontal SIMD op) four times on
every row like the naive version `51565aa5` shipped. The vector sum is bounded
to `V1_BAND_ROWS` = 32 rows of f32 before the f64 upgrade, so this reordering
costs negligible precision (§2.3).

**Protocol** (`benchmarks/era2_perf_break_2026-08-31.md` §22.5 — the noise
floor at these sizes is ASLR, and it is ~10%): one binary, arms selected at
runtime (`ZENSIM_BIGPAIR_TOGGLES`), byte-identical env blocks between arms
(every arm name exactly 3 chars), arms interleaved within each process start,
min of 7 inner walks per start, min over 15 process starts. Three arms:

- `156` — the real production walk, 156-wide output, no free-extras code path.
- `15c` — the wide (944-column) output layout with the four `raw_moments`
  accumulators **off** — isolates the cost of the wider layout alone.
- `15f` — `15c` with the accumulators **on** — the free-superset walk.

Script: `scripts/freefeats_ab.sh` (fixed to stamp the commit via `jj` — a jj
workspace has no `.git` of its own — before this run, `d82b5dfb`). Analysis:
`scripts/freefeats_ab_analyze.py`, which bootstraps (1000 draws, seed
20260901, resampling the 15 starts with replacement) a CI on each ratio
instead of trusting one point estimate. Raw: `ab_raw.tsv` (405 rows, 15
starts × 3 arms × 9 size/thread cells) at
`/mnt/v/output/zensim/freefeats-2026-09-01/ab_raw.tsv`; summary committed at
`benchmarks/free_features_2026-09-01/ab_summary.tsv`.

| size | thr | ratio (median [95% CI]) | verdict |
|---:|---:|---|---|
| 576 | 1 | 1.0081 [1.0065, 1.0162] | CI **excludes** 1.0 — real, +0.8% |
| 576 | 8 | 0.9714 [0.9577, 1.0357] | inside noise |
| 576 | 16 | 0.9866 [0.9671, 1.0470] | inside noise |

| 1152 | 16 | 1.0125 [1.0125, 1.0269] | CI **excludes** 1.0 — real, +1.3% |
| 2304 | 1 | 1.0160 [1.0134, 1.0204] | CI **excludes** 1.0 — real, +1.6% |
| 2304 | 8 | 1.0399 [0.9978, 1.0858] | inside noise (8T is this box's noisiest cell — era2_perf_break §22.5 already flags 8T as the worst-conditioned thread count) |
| 2304 | 16 | 1.0108 [1.0022, 1.0203] | CI **excludes** 1.0 — real, +1.1% |

**Verdict, stated plainly: the raw-moments marginal cost does NOT uniformly
land inside the measurement noise floor — it is priced honestly instead.** At
1T, the cleanest signal (tightest CIs of the three thread counts), the cost is
small and consistently positive across all three sizes: **+0.8% to +1.6%** of
the 156-walk's wall time. At 16T it is smaller but still resolvable for the
two larger sizes (+1.1-1.3%); at 8T — this box's own documented noisiest
thread count — every CI straddles 1.0 and the point estimates are noisier
(0.97-1.04). Nowhere does the ratio show a *negative* trend once threads
scale, so there's no thread-count regime where the batching optimization
(§2.3) failed to help; the residual ~1% is plausible execution cost (four
extra SIMD vector-adds per row, live for the whole band) rather than a
reduce-per-row artifact — the reduce-per-row shape was what the WIP fused.rs
change (this lane, `d82b5dfb`) already removed.

**So: 37 of the 40 raw-moment slots cost roughly 1% of the 156 walk's time to
carry, not zero.** That is cheap — for comparison, §0.1 of the frontier doc
prices the next-cheapest family jump (basic-only → shipped B's masked+IW
arm) at 1.3-1.6×, not 1.01× — but it is not free, and this doc does not claim
it is.

### 2.3 Correctness — bit-identity on every pre-existing slot, precision on the new ones

- `feature_v2::tests::free_extras_are_pure_addition_to_the_v1_only_walk` —
  every pre-existing (156-walk) slot **bit-identical** whether `raw_moments`
  is on or off; the free slots are `+0.0` when off. Unaffected by the fused.rs
  batching change (it only touches code inside `if raw_moments`).
- `feature_v2::tests::free_extras_match_the_944_append_block` — the free
  slots' values against the ground-truth 944 append-block computation: worst
  `|Δ|` moved **4.62e-6 → 5.35e-6** after batching the reduce (still not
  reassociation-free — the append kernel accumulates a whole row in f32 lanes
  where the fused kernel reduces every 16 lanes to f64 — but the batching adds
  its own small reordering on top). Both numbers sit **~2 orders of magnitude**
  below the module's 5e-4 relative tolerance.
- `feature_v2::tests::free_extras_never_touch_a_live_944_walk` — bit-identical
  with append+append2 on, whatever the toggle says.
- Full suite: **246 lib tests + every integration/doctest target, 0 failed**,
  clippy clean on `--features custom-profiles,feature-regime-v2,threads,training`.
  All three gates plus the full suite re-verified on the final rebased tree
  before push (`d82b5dfb`), not carried forward on trust from the recovered
  WIP.

## 3. Quality probe — does the free set close any of ADD156's gap to ssim2?

**Method.** Fits-only, existing tables, columns selected — no re-extraction, per
the mandate. Two owner tools, no new solver:

- `bake_dial_refit gram --parquet ext_safesyn_full.parquet --target human_score
  --target-scale 100 --target-clip-min -100 --space raw --max-feat 944` — the
  registered E-LIN policy (safesyn's human target reaches −739 at ×100 scale;
  13/111,068 rows carry ~40% of the loss uncapped).
- `bake_dial_refit fit-lasso --gram … --slice-file … --lam …` — the
  **coordinate slice is the only thing that changes** between control and
  treatment; same gram, same lambda, same anchor.

Table: `/mnt/v/zen/zensim-training/r1b-pools944-2026-08-30/ext_safesyn_full.parquet`
(111,068 rows, sha256 `e33ec91e…`) — the **`folded720append2pools`** regime
(`V1PoolsMode::Full`), confirmed by direct read (not assumed) to carry f156-371
genuinely nonzero, unlike the ext944-canonical / `*_pure.parquet` roots (whose
"pure" means *purged of synthetic-v2 contamination*, not un-folded — a false
friend caught before it produced a garbage fit). Slice files: existing
`scripts/sota944/slice_basic156.txt` (control, 156 coords — byte-identical to
ADD156's own registered slice) and new `scripts/sota944/slice_basic156_free.txt`
(treatment, 265 coords = 156 + this lane's 109-slot free set: 72 peaks +
37 raw-moment).

**Two lambdas, not one.** λ = 0.002 is ADD156's own registered value, but on
this leg it is nowhere near ADD156's actual sparsity (151/156 active — a
dense, different-shaped model). `benchmarks/hybrid_candidate_2026-09-01.md`
§11.2 already swept λ on this exact leg and found λ ≈ 0.3 lands the 156-only
control at **26 active**, matching ADD156's 28-coefficient regime. Both are
reported; §12.1's own reading is that λ = 0.3 is the operating point that
means something (comparing a dense fit to a sparse incumbent "compares a
hyperparameter to a hypothesis").

**The leg caveat, inherited, not discovered here.** `hybrid_candidate_2026-09-01.md`
§12.1 already measured that this 111k pools leg caps CID22 ~0.05-0.15 below
ADD156's actual 196k-row training leg — which exists **only at v1-372 width**,
so it cannot carry the free-set's f156-371/f720+ weights and is out of reach
without re-extraction (explicitly out of scope here). **So this probe's
absolute numbers do not match the published `ADD156_safesyn_only_raw_lasso`
board row, on both arms equally, for a reason already found and priced by
another lane — not a defect in this method.** The *relative* question (does
the free set help, holding leg + lambda + everything else fixed) is exactly
what "the leg is short but the chain is right" licenses reading off this data,
per §12.2's own precedent.

**Evaluation.** `bake_verdict --regime 944 --cross-regime --features-root
r1b-pools944-2026-08-30` — the tool itself confirmed the root's declared
regime (`folded720append2pools`) before waiving the f156-371 refusal, rather
than the override being a blind bypass. 12-corpus campaign list, both arms,
both lambdas, `--full-json`.

### 3.3 What this does and does not answer

**Does answer:** at ADD156's own sparsity regime, on the one leg available at
944 width, adding the free set (peaks + raw-moments) to the lasso's candidate
pool is a **net positive** on the human-anchored axes that matter most to the
product (CID22 full-range +0.04, CID22 top-band +0.05 pooled/+0.03 per-ref,
KonJND +0.08, CSIQ +0.03, LIVE +0.01), at the cost of a real regression on
SDR25 (−0.06) and a smaller one on AIC4 (−0.02), with 11 more active
coefficients (37 vs 26) doing the work — i.e. the free set gives the lasso
something worth spending marginal L1 budget on, it is not a wash.

**Does not answer:** whether this reproduces at ADD156's real (196k, v1-372-
only) leg — that leg cannot carry the free set without a 944-width
re-extraction, which is out of scope for this fits-only lane and is the same
prerequisite `hybrid_candidate_2026-09-01.md` §12.3 already priced for its own
(unrelated) distillation question. Whoever re-extracts that leg gets this
question re-answerable on the leg that actually matters, for free.

## 4. Hand-off — the free-set definition, for any lane that wants it

**What "free" means, precisely.** 109 slots (944-layout indices) ride along a
v1-basic-only (156) walk at negligible-but-nonzero cost:

- **72 peaks, f156..f227** — already unconditionally computed by
  `fused_vblur_ssim_inner*`; zero marginal compute, `V1PoolsMode::Peaks` ships
  this today. Layout cost of emitting them (wider output vector) is
  unmeasurable (§2.1).
- **37 raw-moment slots** — `733,734,735,750,751,752,784,785,786,801,802,803,
  818,819,820,835,836,837,852,853,854,869,870,871,886,887,888,903,904,905,
  920,921,922,926,931,936,941` (`GLOBAL_DMEAN`/`GLOBAL_CGAIN`/`GLOBAL_CLOSS`
  per scale/channel minus the scale0/ch2 override, + `LUMA_MEAN_REF` per
  scale). Requires `V1FreeExtras::RawMoments` on (`zensim/src/feature_v2.rs`,
  landed `51565aa5`); marginal cost **~1% of the 156-walk's wall time at 1T**
  (§2.2), not zero — price it in, don't assume it away.

**To compute it:** the same v1-only fold walk, with the `raw_moments` toggle
on (`ComputeSet::raw_moments()` / the `V1FreeExtras::RawMoments` flag in
`feature_v2.rs`; bench harness reference: `ZENSIM_BIGPAIR_TOGGLES=15f` in
`scripts/freefeats_ab.sh`). Every other 944 slot needs a plane the 156 walk
doesn't make (`D`, 359 slots), its own pass (`E`, 82), or is a genuinely
different value at this accumulation point (`C-blur`/`C-xch`, 187 combined) —
full classification: `benchmarks/free_features_2026-09-01/slot_classification.tsv`.

**To train against it:** `scripts/sota944/slice_basic156_free.txt` (this
lane's new slice file, additive to the existing `slice_basic156.txt` — the
156-only slice is still there and still correct for a model that should NOT
use the free set). Any `bake_dial_refit fit-lasso --slice-file` or
`zensim_mlp_train --keep-features` call can point at either. **Needs a table
at the `folded720append2pools` (or wider, genuinely non-folded) regime** — the
default `ext944-canonical` / `*_pure.parquet` roots zero f156-371 and will
silently zero the peaks half of the free set (§3, the "false friend" caught
before use).

**What it bought, measured (§3):** at ADD156's sparsity-matched operating
point, a real but partial close of the gap to ssim2 on `hfnl_cid22band`
(+0.05 pooled / +0.03 per-ref, ~30% of the remaining gap) and on full-range
