## Findings

**1. The audit understated the defect.** Baseline G-RANGE fails **8 of 14**
corpora, not 4 of 8 — LIVE, CSIQ, KADID and TID fail too (27–38 % of rows below
the bottom knot). The audit's 8 rows reproduced exactly.

**2. The fix splits into a free half and a costly half.**

*Arm A — spline-top extension — is FREE and should land.* Rank-exact on every
corpus, and it fixes the entire near-lossless failure this profile is sold on.
Independently re-verified here with the post-fix binaries:

```
hf_nearlossless G-RANGE   baseline: above-knot 300/300 (100.000%) FAIL
                          arm A   : above-knot   0/300 (  0.000%) PASS
rank Δ (bake_verdict, 6 corpora): cid22 +0.000000  konjnd +0.000000
      live +0.000000  csiq +0.000000  kadid +0.000000  tid −0.000002
```
G-RANGE goes 6/14 → 8/14 PASS; dial G-DYN *improves* 85.535 → 85.767.

*The winsor guard costs real rank.* It takes G-RANGE to **14/14**, but by
clamping the severe rows that carried the rank signal: **LIVE −0.045,
KADID −0.036, TID −0.026** (arm C; arm B is worse on each), and it compresses
the dial's low end (G-DYN −3.4, p5 9.5 → 13.2). **Treat as a separate,
user-gated trade — do not land it silently.** Prefer arm C over arm B.

Two winsor hypotheses were **falsified**: fitting on safesyn (ADD156's own
training data) gives windows too wide to guard anything, and adding 10 k
KADIS negative-rich rows widens them until the guard vanishes entirely.
`B`'s registered fit corpus works but is **circular** on this gate row — its
200 NL refs are a strict superset of `hf_nearlossless_val`'s 50 — so arm B/C
drop those 50.

**3. `n_feature_bounds: 0` is a MISLEADING symptom.** Shipped `B` reports 0 too.
The OOD guard is carried as 372 `zentrain.feature_transforms` = `winsor_p99`
entries, not in the `feature_bounds` section. The audit's D7 symptom line
should not be read as "B has bounds and ADD156 does not".

**4. NEW DEFECT — `pack` cannot carry this fix.** Measured four ways:
`pack` *always* refits the spline over its anchor, replacing the extended
[0.301, 1.721] domain with an in-distribution one — packing arm A yields a bake
**byte-identical** to the packed baseline (`879409d3…`), i.e. **the fix is
erased**. On a winsor bake the refit raises the bottom knot 0.301 → 0.44/0.48
and re-opens below-knot (PIPAL 0 → 12.0 %, LIVE 0 → 34.7 %). `extend-top` after
a pruned pack is structurally impossible (`feature_transforms has 372 tokens,
expected 28`), and `pack --no-prune` forfeits the whole size win because
ADD156's 3,575 → 837 B *is* dead-column pruning. **So there is no packed form of
ADD156 that passes G-RANGE with today's tools** — ship the unpacked form, which
is exactly how Profile `B` ships (7,325 B, unpacked). Not fixed here.

**5. The missing tool.** A spline *bottom* extension — the rank-free counterpart
to `extend-top` — has no owner. `bottom-extend` pins `(floor_raw, 0.0)` and
ADD156's bottom knot already *is* `(0.3008, 0.0)`, so it would flatten 27–38 %
of KADID/TID/LIVE/CSIQ into a tie at 0 and delete the negative tail (audit D4).
Building it would make D7's remaining half free.

**6. Open question about the gate itself.** ADD156's bottom knot *is* the dial's
zero, so "below-knot" on this bake means "scores below 0" — the product's
documented negative tail — not an undefined regime. `bake_dial_refit gate`
cannot distinguish the two, so its below-knot rows over-count the defect on any
bake whose spline bottoms out at 0.
