# Rev5 ordered strip batching (2026-10-09)

Rev5's streaming walk previously consumed each producer strip before asking
for the next. The dense and gradient kernels inside a channel task were serial;
scale zero has only one live channel. This limited available independent work
while each basic-band fan-out still joined the Rayon pool. The historical
COSTCMP executable's 4096² diagnostic consume occupancy was 0.185 at 8 threads
and 0.048 at 32 threads (busy time / wall time / requested workers). These are
instrumented phase observations, not qualified scoring timings.

The new path queues bounded owned halo windows, evaluates the existing whole
128-row kernels and 32-row basic bands in parallel, then merges each partial in
producer order. Basic bands remain individually ordered; their sums are never
first combined into strip sums. Sparse blockiness still visits the original
pixel lattice in order. Retained-map walks and pools below eight threads use
the existing route. The queue holds at most 16 jobs, independent of image
height, and reuses its scratch across calls.

Strict before/after replay passes 384 of 384 Rev4/Rev5 score and 420 consumed
feature comparisons over eight geometries, four tiers and six thread counts;
all 576 frozen comparisons, including Rev3, are unchanged. The existing Rev3
tolerance failures remain recorded in both receipts. A separate native test
checks every emitted feature bit at 8/16/32 threads against serial execution,
including partial strips, strided input, identity pairs and scratch reuse.
`cargo test -p zensim --all-features`, workspace CI-exact clippy and COSTCMP
benchmark clippy pass. The checks wrapper reports rc=0, 248 seconds,
peak RSS 1.77 GiB, minimum available RAM 41737 MiB and peak load 8.19.

Raw evidence and frozen executables live at
`/mnt/v/output/zensim/rev5perf4-2026-10-09/`. Reproduction recipes are in
`benchmarks/rev5perf4.just`; profile recipes require an outer shared lock and
`run-heavy`, while COSTCMP timing owns its per-segment `--lock`. The scaling
preset pairs after Rev5, Rev4, serving A/B and a frozen before Rev5 executable
in the same 32 admitted rounds. It includes the 24 requested scaling cells and
24 controls at 1/2/4 threads. The original quiet gate and first-32-clean-of-at-
most-64 admission rule are unchanged.

Diagnostic phase reports reset counters but divide repeat N by cumulative
walk count N. Multiply the displayed milliseconds by N to recover that
interval's actual elapsed milliseconds. Profiler wall times and affinity
experiments do not qualify as timing receipts. Cache-miss counters alone do
not measure DRAM bandwidth or establish false sharing.

The queued scratch now retains eleven planes per job. Once vertical blur
finishes, two horizontal intermediates become the activity-chain temps;
these reuse the same existing blur and abs-difference kernels. The append
bs2 plane is unused by Rev5 and is never allocated for a queued job. Parent
scratch reserves horizontal planes only when a basic-only scale can reach
the original path, and reserves no vertical planes for batched cells.
Sparse scale requests are included in the strided scratch-reuse parity test.

The final bounded-scratch build again passes all-feature tests and clippy.
Its checks wrapper reports rc=0, 317 seconds, peak RSS 3.05 GiB, minimum
available RAM 41527 MiB and peak load 6.63. The repeated strict gate still
passes 384/384, and all 576 frozen before/after comparisons are unchanged.

## Profile findings

Fresh before/verified perf workloads at 4096² run one initial scoring call
and sixteen repeats. The process totals include setup and are diagnostic;
they are not clean-round scoring measurements.

| requested threads | before process seconds | verified process seconds | before cache misses | verified cache misses |
|---:|---:|---:|---:|---:|
| 8 | 3.092963623 | 2.373394581 | 235849451 | 614597773 |
| 16 | 3.658275526 | 2.469386511 | 424543392 | 722191671 |
| 32 | 3.723524735 | 2.568582336 | 489197577 | 747607207 |

The before 16-thread workload took 3.658275526 seconds on physical cores
across both CCDs, versus 3.160161654 seconds on CCD0 with SMT. Eight threads
on CCD1 took 3.604607612 seconds, versus 3.092963623 seconds on CCD0. The
resolved CPU topology is recorded alongside the profiles. These affinity
experiments support a cache-placement contribution; they are not evidence
of a specific DRAM bandwidth ceiling. No direct bandwidth or cache-line
sharing measurement was made.

Before batching, the 32-thread 1024² perf report attributed 22.11% of
samples to crossbeam epoch handle work associated with stealing. The
initial batched build reduced that to 8.62%; the final build has its own
full perf reports. Increasing the pool no longer expands only the idle
stealing population, but residual serial producer work, halo copies and
cache traffic remain. New consume spans include queued blur work, so phase
names do not denote identical stage boundaries across implementations.

The eight-job trial reduced queued scratch but its 32-thread diagnostic
4096² warm median was 154.908 milliseconds, versus 141.012 milliseconds
for the initial 16-job path (reconstructed from rounded phase reports).
The retained path uses sixteen jobs and instead reduces each job's planes.
Both trial executables and their raw observations remain in the raw root.

Fresh-process heaptrack at 4096² reports the following peak heap values
in its printed decimal units; these include input/model setup. Heaptrack
RSS includes profiler overhead, so the final native RSS table uses separate
`/usr/bin/time -v` observations.

| requested threads | before peak heap | verified peak heap |
|---:|---:|---:|
| 8 | 241.59M | 380.79M |
| 32 | 241.77M | 581.33M |

This is a speed/memory tradeoff. Storage is bounded by strip width and the
job cap, rather than image height; peak memory still increases. The final
profile/check wrapper reports rc=0, 70 seconds, peak RSS 0.54 GiB, minimum
available RAM 44670 MiB and peak load 3.53. Allocation profiles cover initial
calls; they do not establish a steady-state allocation count.
