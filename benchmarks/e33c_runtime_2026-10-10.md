# E33C_RUNTIME: arm C's runtime-guard failure, its cause, and the fix (2026-10-10)

E33 adopted arm A by the registered rule. Arm C (fx1: 410 differences + 410 difference × fragility products,
820 inputs) failed two gates. One was the registered §9.3 runtime guard: no cell slower, meaning no paired 95% CI
wholly above +2% of production. C was +25.9% / +26.6% at 64² and +5.8% / +7.3% at 256² (v3 / v4x, 1 thread),
and −1.0% / −0.3% at 1024². That pattern means a fixed per-call cost. This record finds that cost and removes it
without changing an output bit.

**Landing status (2026-10-10).**
- Only the zensim plan cache is on `main`. zensim still pins zenpredict `05de3cbc`.
- The zenpredict half (zenanalyze `417cc785`) is held. An effort-xhigh review found that it slows the shipped
  profiles' `Zensim::compute` path, which runs `Model::from_bytes` on every compare. Score bits stay equal, but
  each compare now decodes the whole f16 layer. Medians, one thread: profile C +29.7% at 64² and +3.3% at 256²,
  profile A +13.9% at 64².
- This record timed only the `BakeScorer` path, which parses once. The profile path was not timed here.
- The verdict below was measured with both halves. The plan cache alone (about 55% of C's extra cost by the
  profile below) was not timed against the guard, so the guard verdict for `main` waits for the zenpredict change
  to land with a fix: zensim caching the parsed profile model, or a lazy decode.
- Review evidence: `/mnt/v/output/zensim/e33c-runtime-2026-10-10/`.

## Cause

Profiled with `perf` on the registered gate binary: C against A at 64², one thread.

1. **The extraction plan was rebuilt on every score (about 55% of C's extra).**
   - The call chain is `BakeScorer::compute` → `plan()` → `Plan::for_bake(model)` → `bake_read_slots`.
   - For C that re-parsed the 820-line `zensim.derived_inputs` declaration and scanned its 104,960-weight
     layer 0.
   - Every bake paid the generic part of the rebuild; C paid the declaration parse and a doubled layer-0 scan.
2. **The f16 first-layer matmul decoded each weight on every call.**
   - zenpredict's `saxpy_matmul_f16` used the branchy software `f16_bits_to_f32` per weight, so the loop did not
     vectorize: about 0.74 ns per weight on v3.
   - C's layer 0 is twice A's (104,960 against 52,480 weights), so about 40 µs more per call.

Product construction (820 f32 multiplies), allocation and input marshalling did not appear in the profile.

## Fix

- **zensim:** `BakeScorer` caches `Plan::for_bake(self.model)` in a `OnceLock`. That plan depends only on the
  model and the process formula revision, which is itself a process `OnceLock`. Composition (members, weights,
  the corruption companion) still runs per call.
- **zenpredict (zenanalyze repo, separate change):** `Model` decodes each f16 layer to f32 once at load, using
  the same `f16_bits_to_f32`, and runs it through `saxpy_matmul_f32`. That kernel has the f16 kernel's exact
  loop, zero-skip and `fma` order. The cost is 4 bytes per f16 weight.

## The registered runtime cells, re-run

- **Method:** the same harness (`costcmp_run.py --e33-grid`, registered E33 arms) and the same unchanged
  quiet gate, on a fresh raw root.
- **Rounds:** first 32 clean rounds of at most 64; 14 noisy attempts were excluded and kept as `.bak`.
- **Lock:** 21 lock acquisitions and 21 releases.
- **Load:** the highest admitted load1 was 1.93.
- **Statistics:** the paired analyzer is COSTCMP's (`798d9386…`).
- **Binary:** `instrument-fix2` (`11c49660…`).
