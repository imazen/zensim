# CHDR_PU: the HDR candidate CHdr through the PU-linear HDR entries (2026-10-10)

`ZensimProfile::CHdr` is the HDR candidate-of-record (frozen 2026-08-28 as `HDR944_L1T1_s4005_hfpack`; Sept 7
dense bake `c_hdr_l1t1944_byid_2026-09-07.bin`, 697 declared ids of the 944 folded layout, declared revision Rev1).
`Zensim::compute_pu_linear` is the documented primary HDR entry point. On `main` (`ba19d54b`) it refused CHdr.

## Diagnosis

Synthetic HDR pairs (0.1–1,800 cd/m² textured ramp, every seventh sample brightened 8%) at 17×19, 64×64, 97×65 and
256×128. Every profile went through five entries: `compute_pu_linear`, `compute_pu_linear_planar`,
`compute_pu_linear_extended_features`, descriptor-HDR `compute` (an `is_hdr()` `LinearF32Rgba` source) and an
identical pair. That makes 160 cells per revision.

- **Before, default revision (Rev1):** C and CHdr are refused on interleaved, planar, extended and descriptor input,
  at every size, with `ModelForwardFailed` ("the bake declares feature ids this feature vector does not reach").
  B, BHdr, A, D, PreviewV0_1 and PreviewV0_2 serve. The identity short-circuit returns 100 for everyone.
- **Cause:** below Rev5 the PU entries run the legacy buffered PU walk, which emits only the v1 vector: 372 wide
  for C/CHdr's extended + IW config. They never ask for the bake's plan. CHdr reads ids up to the 944 layout,
  so the dense gather (`metric.rs`, `apply_mlp_scoring_with_codec`) refuses the short row. SDR `compute` asks
  `scoring_plan`, which returns a plan exactly when a bake reads past the v1 width, and serves.
- **Not a feature-gate problem:** C and CHdr need `candidate-profiles`, which implies `feature-regime-v2`. The
  failing all-features build has every feature.
- **Rev5:** C/CHdr configs are fold-backable, so the PU entries already took the planned fold, and still refuse
  with the same message. Both bakes declare Rev1 (measured with `bake_formula_revision_public`), and SDR
  `compute` refuses them identically in a Rev5 process. This is pre-existing and shared by both entries, and
  the message does not name the revision mismatch. Not changed here.
- **`compute_pu_linear_extended_features`** is an explicit extraction of the 372-wide extended layout. A 944-layout
  bake cannot be served from it by construction, so it keeps refusing.

## Reference extraction

CHdr's training and validation features came from the fleet's `zensim-foldapp2` metric on HDR pairs:
`benchmarks/hdr944_bake_wave_2026-08-27.md` (L1 design: "hdrfeat944 (944-regime, `zensim-foldapp2`,
HdrEncoding::Linear arms)"; L1-T2 table `hdrgrid-mc944-t2-2026-08-27`). The retrain wave that produced
`HDR944_L1T1_s4005_hfpack` reuses those mc944 legs (`benchmarks/hdr944_retrain_wave_2026-08-28.md`). The code
behind that metric is zenmetrics `crates/zenmetrics-cli/src/hdr.rs` `hdr_foldapp_features`. It wraps decoded
absolute-nits images as opaque `LinearF32Rgba` sources and calls
`Zensim::compute_folded720_append2_features_hdr(…, HdrEncoding::Linear, V2NewFeatureToggles::default(), …)`. Its
default toggles have append2 dst-activity off, the canonical variant the Sept 7 correction moved serving onto
(`benchmarks/feature_plan_cleanup_2026-09-07.md`).

**Equality is with today's build of that extraction, not the fleet-era build.** The review (CHDR_PU_REVIEW,
2026-10-10, Q2) rebuilt the fleet-era zensim (`6a0f03ae`; glibc and musl agree bit for bit). Against it, today's
extraction and today's served CHdr vector differ at up to 320 of 697 ids: v2 372–719 and append 720–919 move,
while v1 and append2 are exact. The largest difference is 1.10e-5, and CHdr's score moves by at most 1.5e-4
points. Two deliberate, recorded changes, both after the training extraction, account for all of it:
`7ee3cdce` (exact MSCN normalizer in place of the vendor-dependent `rsqrt`) and `515001dc` (the user-decided
ERA-2 fixed-lane dense accumulation). This is pre-existing train/serve drift, not something this fix introduced.

## Fix

`Zensim::pu_fold_route` (private) decides which walk `compute_pu_linear` and `compute_pu_linear_planar` take.
Descriptor-HDR `compute` routes through the former.
- **Rev5, fold-backable config:** the canonical PU fold, as before.
- **Below Rev5, a scoring plan wider than the v1 vector (C, CHdr), no stop token:** the same planned fold,
  `compute_pu_fold` (`HdrEncoding::Linear`, the plan's toggles and compute set). This is SDR `compute`'s rule in
  `compute_with_config_inner`, with both of its conditions:
  - a live stop token keeps the request on the buffered walk (issue #48: the fold has no intra-walk stop hook).
    For C/CHdr that walk cannot reach the declared ids, so a stoppable request is refused with exactly SDR's error;
  - identical pixels return 100 with zeros at the plan width, without walking.
- **Everything else:** the legacy buffered PU walk, unchanged.

The plan comes from `cached_pu_plan`, one `score_plan` per (profile params, skip flag, v1 width) per process, and
`compute_pu_fold` takes it as an argument. A profile the legacy walk reaches pays one map lookup per call, not a
plan derivation. No public API changes, and no steering files (`feature_v2.rs`, `local_refine.rs`,
`attribution.rs`, `metric/bake.rs`) were touched.

**First version and review.** The first fix (`c7c9591a`) called `scoring_plan` on every PU call and ignored the
stop token. The CHDR_PU review measured both problems:
- B, A and D PU calls were 0.6–29% slower;
- a stoppable CHdr request took the fold, so cancellation came 174–178 ms after the token fired instead of within
  a band.

This version fixes both; the measurements are below.

## Results

**Regression tests** (`zensim/tests/chdr_pu.rs`):
- `chdr_scores_through_the_pu_entries_and_matches_its_validation_extraction` fails before the fix (17×19:
  refused) and passes after. At four geometries:
  - interleaved, strided interleaved (row padding 5), planar, strided planar (padding 3) and descriptor-HDR inputs
    agree on score bits and the full feature vector;
  - the served features equal today's build of the reference extraction bit for bit at all 697 declared ids;
  - the served score equals `score_features_with_profile(CHdr, reference)` bit for bit;
  - an identical pair scores 100.
- `a_stoppable_wide_plan_pu_request_follows_the_sdr_cancellation_contract`, for C and CHdr:
  - without a token, PU and SDR both serve;
  - with a never-firing token, PU interleaved, planar and descriptor-HDR refuse with exactly SDR `compute`'s error;
  - a fired token returns `Cancelled`;
  - B keeps its PU bits under a never-firing token.
- `wide_plan_pu_identity_matches_sdr_identity`: C/CHdr PU identity is 100 with zeros at SDR's identity width.

**Census.** The review's probe compares `main` `abf16097` against this fix. It covers 8 profiles × 10 entries × 22
geometries × 2 contents × parallel on/off × 4 tiers × 5 revisions: 74,880 rows per tree, comparing status, score,
raw distance, mean offset, the feature-vector hash and the refusal text.
- **Other profiles:** B, BHdr, A, D, PreviewV0_1 and PreviewV0_2 are identical in **53,520/53,520** rows (49,280
  served, 4,240 refusals).
- **C/CHdr at Rev1:** interleaved, strided, planar, strided-planar and descriptor-HDR rows go from refusal to a
  score. The served score equals the reference recomputation and `BakeScorer::compute_hdr` in 880/880 cells each.
- **C/CHdr at Rev2–Rev4, non-identity:** the PU refusal changes from "does not reach" to the revision-mismatch
  message ("wide feature extraction requires matching process and requested formula revisions"; at Rev4,
  "formula revisions 4 and 5 cannot be mixed…"). SDR `compute` still serves C/CHdr there with its cross-revision
  "not a served score" warning; PU refuses, like `BakeScorer::compute_hdr`.
- **C/CHdr identity, Rev1–Rev4:** the score stays exactly 100. The feature vector is now zeros at the plan width
  (942 for C, 944 for CHdr) instead of 372 zeros, matching SDR's `identical_result_at`.
- **Unchanged C/CHdr rows:** all 240 live-stop-token rows and every Rev5 row, along with SDR, SDR-extended and
  both extended PU entries.

**Cancellation.** The review's probe used a 2048² HDR pair at Rev1 with 8 threads, firing the token at about 20% of
the call:
- **B:** `Cancelled` 57.3 / 54.1 ms after the fire;
- **CHdr, now on the buffered walk:** `Cancelled` 29.2 / 33.1 ms after the fire. On the first version it took

PU entries. `params_pu_linear` maps only `B` to `BHdr`; the owner decides (CHDR_PU_FIX_DONE).
