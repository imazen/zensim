## 3. The pin mechanism — three candidates, and why only one can work

The identity feature vector is the **zero vector** for every image (gate doc §4, re-verified
here: all 38 rows of the pinned identity probe are exactly 0.0 on all 372 columns). D is a
single linear layer with no feature transforms, so

```
raw(x)   = ȳ + Σ_j w_j · (x_j − μ_j)/σ_j          dial(x) = spline(raw(x))
raw(0⃗)  = ȳ − Σ_j w_j · μ_j/σ_j                   ← a SCALAR property of the bake
```

| candidate mechanism | what it changes | verdict |
|---|---|---|
| **bias offset** (`b += δ`) | every raw by the same δ | **provable no-op** (§3.1) |
| **anchor row with high weight in the FIT** (an identity Gram group) | `w`, `μ`, `σ`, `ȳ` | **real re-fit — and measurably does not pin** (§4) |
| **identity rows in the ANCHOR/SPLINE step** | the spline only | **the one that works** (§5) |

### 3.1 Why a bias offset cannot move the identity dial — exactly

`fit_spline_knots` places knots at *percentile edges of the prediction distribution* and takes
the per-bin median of `(pred, target)`. If every prediction shifts by δ, every percentile edge
and every bin median shifts by δ and every target median is unchanged, so the refitted spline
is the old spline translated: `spline'(x) = spline(x − δ)`. PCHIP derivatives are
translation-invariant too. Therefore

```
dial'(input) = spline'(raw(input) + δ) = spline(raw(input)) = dial(input)      for EVERY input,
```

identity included. A bias offset is a reparametrisation of the raw axis that the calibration
step undoes exactly. **The quantity that decides the identity dial is `raw(0⃗) − raw(grid)`,
which no bias offset changes.**

*(The direct instrument for this — shift the weights with `affine_calibrate`, then re-fit the
spline — could not be run: `affine_calibrate` cannot read a current compressed ZNPR v3 bake.
It hand-parses the layer table and reads `out_dim = 16777472`, asserting at
`zensim-validate/src/bin/affine_calibrate.rs:80`. Reported, not fixed — it is not on this
lane's path, and the empirical null in §4 is stronger anyway: it moves the intercept by
**+0.0464**, 1.7× the +0.0272 a pin would need, and the identity dial does not follow.)*

## 6. `D-id100-negrich` — and an owner defect found on the way

The registered lever for the floor axes was "the anchor/fit rows extended with negrich rows
carrying unclamped negative targets". **No new data was needed.** The multiband anchor already
carries `ssim2_gpu` at full depth — verified: `target_score == max(ssim2_gpu, 0)` on all 2,000

### 6.1 The defect: the neg-tail dedup was deleting real negative knots

`dial_spline::fit_spline_knots`'s `neg_tail` dedup selected its run with `cy[i] <= 1e-6`. Its
documented intent is a run of **zero** knots — the `y == 0` plateau a *clamped* anchor
produces. With an unclamped anchor that predicate matches **every genuinely negative knot**, so
the dedup deleted the negative tail's structure and kept only its shallowest member.

MEASURED, before the fix, on an anchor holding 2,147 negative rows spanning ssim2
−1437.97 … −0.74: the fitted bottom knot came back at **y = −12.16** with 10 knots surviving.
Since `output_calibration_spline::apply` floors the downward extrapolation at
`ys[0] − (ys[n−1] − ys[0])`, that capped the dial's whole negative tail at **−124.33**.

**Fixed** (`zensim-validate/src/dial_spline.rs`): the predicate is now `cy[i].abs() <= 1e-6`.

**BYTE-INERT for every clamped anchor** — when no `y` is negative the two predicates select the
same indices. Gated three ways:
- `neg_tail_dedup_is_byte_inert_on_a_clamped_anchor` — `to_bits()` equality of every knot
  against the pre-fix predicate, at n = 200/1000/2000.
- `neg_tail_dedup_keeps_genuinely_negative_knots` — carries its own negative control (asserts
  the pre-fix predicate *did* have a run to collapse).
- **The real recipe:** the §1 control still reproduces `51437a34…` and `4481c2d4…`
  byte-for-byte after the fix, and `D-id100` (clamped anchor) is byte-identical pre/post.

Post-fix, the same negrich anchor yields a **19-knot** spline with `ys[0] = −56.57` and a
negative tail reaching −213.

### 7.1 The two axes that remain, and why — both measured, neither a tuning failure

**A9 (`frac_below_zero ≥ 1.0`) is not attainable by ANY output spline on D's ordering.** For
every one of the 2,000 all-negative probe rows to read below zero, the dial's zero-crossing
must sit at or above the probe's *maximum* raw prediction. That maximum is **+23.135** — an
OOD outlier, on a grid whose entire raw span is [−0.062, 0.972]. A zero-crossing at 23.1 maps
the whole dial grid below zero. Even the 99th percentile requires a crossing at raw **0.7823**,
inside the grid's own mid-range. **A9 is a model-ordering limit, the same class of result as
§10.3's C2 ⊻ C6 proof for B — and the gate doc already records A9's `1.0` as definitional
rather than empirical.** For reference, D reads `frac<0 = 0.5625` in raw space; the spline
raises it to 0.914.

**A7 (negtail `min ≤ −770.62`) is bound by the OOD floor formula, not by the anchor.**
`output_calibration_spline::apply` floors the downward extrapolation at
`ys[0] − (ys[n−1] − ys[0])` — one calibrated dial-range below the bottom knot (the 2026-07-10
OOD safety net, product parity). With `ys[n−1] = 100` that is `2·ys[0] − 100`, so
**A7 requires `ys[0] ≤ −335.3`**: the anchor's bottom-percentile bin median at −335, where
only **0.170 %** of `kadis_negrich`'s negative population sits (404 of 237,675 rows). §6.2
measures what forcing it costs — A2 and A5 break first. **A7 is reachable only by changing the

## 9. The ssim2 exam (`benchmarks/ssim2_replacement_bar_2026-08-31.md`) — inherited, and why

The forward pass is **byte-identical** to shipped D: same 372 declared inputs, same

absent transforms. The support did **not** change, and `n_inputs` did **not** change. Only the
output-spline metadata differs.

## 10. Ship proposal — for the user to decide. **NOTHING IS FLIPPED.**

`D-id100-negrich` is the recommendation if a dial default is being chosen on the gate the user
declared a hard ship gate. What it would change for users of `ZensimProfile::D`:

- **A perfect copy reads `100.000` instead of `96.116`.** Nothing on the dial grid out-scores
  it, before or after (0 of 4,424 cells, unchanged).
- **The top of the dial moves up.** Grid max 96.049 → 99.380; `p95` 95.284 → 95.518. In the
  near-lossless band the dial reads **up to +3.3 points higher**, and it is *closer* to the
  reference metric there: ssim2's own grid max is 98.377, which shipped D undershot by 2.33.
- **The bottom of the dial moves down, a lot.** Grid min −12.204 → −57.172; the deepest
  negative-tail probe row −100.000 → −213.149; the fraction of an all-negative population that
  reads below zero 85.8 % → 91.4 %. This is the *product contract* behaviour
  (CLAUDE.md: *"NEGATIVE zensim values MUST work"*) working further out, not a regression.
- **Reach 108.252 → 156.551**, past ssim2's 153.731 for the first time in this lineage.
- **Rank does not move.** Bit-identical on 12 of 14 corpora, ≤ 8e−6 on the other two, zero
  pair-order flips anywhere, `product_composite` byte-identical.
- **Speed does not move.** Byte-identical weights; the spline is 19 knots vs 30.
- **Cost:** any stored zensim-D number is on a different dial. Per-cell shifts on the canonical
  grid are large by construction at both ends — this is an **era break for the D dial**, and
  every D-scored table would need re-reading, exactly as `docs/DATASET_HISTORY.md` treats an
  era. If that break is not wanted now, `D-id100` (the identity pin alone, 4/9) is the smaller
  move: same C5 fix, top-end only, `p5` moves 9.517 → 9.636.
- **What it still does not do:** A7 and A9 fail, for the measured structural reasons in §7.1.
  Neither is a tuning gap. `D-id100-negrich` is not "as good as ssim2 at the ends" — it is
  7 of 9 axes there, against shipped D's 2 and shipped B's 3.
