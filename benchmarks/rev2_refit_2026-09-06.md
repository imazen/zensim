## 1. Why the shipped D chain cannot be run verbatim on the R6b tables

Measured before fitting anything, because it decides what the A/B can be:

* the R6b safesyn leg's target is the **same column as the canonical training
  leg's, ×100** — `human_score / 100` is **BIT-IDENTICAL** (max\|Δ\| = **0.000e0**)
  to `canonical-2026-05-21/train/safesyn.parquet` on all 196,086 rows in order.
  KADID (10,125) and TID (3,000) are likewise **0.000e0**. So the R6b legs are
  the canonical legs re-extracted, not a different sample;
* but the shipped D's own gram
  (`linear-probe/grams/safesyn.npz`, `904a8e80…`) is an **earlier extractor +
  decoder era**: its per-feature means differ from the R6b `ratio` (= revision-1)
  arm's on **372 of 372 slots**, median 1.2 %, p95 17.7 %, max 25.5 %;
* and its target is a **different column entirely**. The shipped gram's is in
  [0, 1] with ȳ = **0.768047**; the canonical safesyn leg's (= R6b's ÷ 100) is
  ȳ = **0.600005**, on the same 196,086 rows. Rescaling cannot close that, and
  neither can clipping: R6b's clipped at 0 and divided by 100 gives **0.6156**,
  not 0.7680. So the shipped D's gram was built from a **different 196,086-row
  safesyn table** than the canonical training leg the R6b lane re-extracted —
  same corpus, different measurement.

`fit-lasso`'s `--lam` acts on the mean-loss scale with the FEATURES
standardized and the TARGET not, so `ρ` scales linearly in `y`: at
`--lam 2e-3` on a ×100 target the R6b lane's own fits carry **147** active
coefficients where the shipped D carries **28**. That is a different model
class, not the D lineage.

**So the single-variable A/B is `ratio` (revision 1) vs `satexcess` (revision 2)
on the R6b tables, both through the identical shipped-D chain**, with the gram
built at `--target-scale 0.01` so `--lam 2e-3` means what it means in the
shipped recipe. That choice is validated by its outcome rather than asserted:
the revision-1 in-era arm lands at **exactly 28 active coefficients**, the
shipped D's own count.

The identity anchor needs no substitution decision at all: **the identity
feature vector is the zero vector at BOTH revisions** (verified: the shipped
21-row anchor and R6b's 400 self-pairs are all-zero, 372/372, in both arms), so
the 21-row anchors cut for the two arms are **byte-identical to each other**
(`a8a0a0e89bc8678e…`) and structurally identical to the shipped one — same
zeros, same target 100. Gated, not assumed.

## 5. G-SHIP.5 — perf. The wall-time cell is NOT MEASURED; the kernel cost IS

**The W4 wall-time cell is NOT MEASURED, and the reason is the box.** A sibling
lane of this same wave (`zenmetrics--rev2wave/crates/zensim-gpu`, the §1 GPU
copy) held **~27.7 of 32 threads** for the whole of this lane's window. This
repo's own measurement protocol
([`CLAUDE.md`](../CLAUDE.md) "PERF MEASUREMENT" and
[`benchmarks/profile_d_notax_2026-09-01.md`](profile_d_notax_2026-09-01.md) §4)
says outright that a taskset-pinned wall-time sweep taken while anything else
runs is contaminated, and that a harness under a tight budget can report a
spuriously LOW mean that `min()` will happily select. So no wall-time number is
offered here.

**Instruction counts are not load-sensitive, so the kernel-cost question IS
answerable, and it was answered.** `callgrind` on
`zensim/examples/foldapp_stream_bigpair` with `ZENSIM_BIGPAIR_TOGGLES=372`
(the v1-372 walk, which is Profile D's class), one binary, arm chosen at
runtime, `ZENSIM_FORMULA_REV=1` vs `=2` — the two env values are the **same byte
length**, per the layout rule this repo learned the hard way:

| run | Ir | vs rev1 run A |
|---|--:|--:|
| rev1, run A | 56,680,668,779 | — |
| rev1, run B (**determinism control**) | 56,680,668,822 | **+43 (+7.6e-10)** |
| **rev2** | **56,700,592,219** | **+19,923,440 (+0.03515 %)** |

The control makes the reading interpretable: callgrind repeats to within 43
instructions, so the rev2 delta is **462,000× the control's own noise** — it is
real and it is **3.5 parts in ten thousand** of the walk. That is what "one
`max` and one divide on already-loaded values, outside the pixel loop" predicts.

**G-SHIP.5 verdict: the stated expectation (no meaningful kernel cost) is
CONFIRMED at the instruction level and NOT MEASURED at the wall-time level.**
Re-run the W4 cell on a quiet box before quoting a time.

### 8.3 A defect found and fixed in the negrich builder (owner extension)

`build_negrich_postc.py` read the row index from the extractor CSV's
`human_score` column. The header-driven `--corpus pairs-tsv` loader recognises
only a column literally named `human_score`; a pairs TSV that names its index

name**, and `human_score` comes back 0 for every row. **MEASURED: 60,000 rows in,
1 row out, no error and no warning** — the dict keyed on the index collapsed to
a single entry. Fixed by adding `--idx-col` (default `human_score`, so every
existing invocation is unchanged) with the failure written into its help text.

### 8.6-pre A prediction, written before the revision-2 head was fitted

Registered here so it reads as a prediction and not as a story told afterwards.
`satexcess` is a **strictly increasing** function of `g` (H5, measured: 0
inversions), so any model whose decisions depend only on the ORDER of a feature
is invariant to it. That splits the three arms cleanly:

* **`hgb` and `hgb_drop8` should be nearly unchanged.** A gradient-boosted tree
  splits on thresholds; a monotone reparameterisation moves where a split value
  sits, not which rows fall either side. `HistGradientBoostingClassifier` bins
  to 255 quantiles, so the only leak is rows landing in different bins, which is
  second-order.
* **The `logistic` should IMPROVE MORE, and it is the arm with the mechanism.**
  It is linear in the feature value, and `fit_probs` standardizes then **clips
  at ±8**. §8.2 measures the negrich leg carrying `contrast_inc` up to
  **1.22e7**, with 26.0 % of cells over 1 and 0.71 % over 100. Revision 2 maps
  the whole range into `[0, 1)`, which puts those rows back inside the linear
  model's dynamic range.

**Amended before the numbers, because the first draft of this prediction was too
strong.** The ±8 clip is applied to EVERY arm, tree included, so within the
clipped group the ordering is destroyed for the tree as well and `hgb` can move
too. The distinguishing claim is therefore only the RELATIVE one — the logistic
should gain more than the tree — and if the tree moves more, the mechanism above
is wrong and the write-up will say so.

### 8.6b The board graft path is proven, and it reports the HEAD-ALONE rule
