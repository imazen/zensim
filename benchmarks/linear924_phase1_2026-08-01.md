# E-LIN phase 1 — can the linear family beat Profile B on 924-regime data? (pre-registered 2026-08-01)

**Question.** Profile B (`zensim/weights/b_sdr_linear_cid80_inclwinsor_dense_dial_2026-07-07.bin`,
sha256 `b6fe5233ee9c752d29abeb8be8b0814c052dd96f566a82250cdd6ff6a8cb13e0`, n_inputs=372) is the
best shipped LINEAR model: CID22 SROCC 0.87638, KonJND 0.54665, dial mono 97.92% / tied 0.0%
(its `.metrics.json`). The E-M campaign showed the CID22 lift of the 924-era MLPs is mostly
DATA (E-M6b). The linear class has never seen the v3/append features, the 924-era mixes, or
the negrich tail. This phase asks: does fitting the SAME linear family on 924 features + data
beat B — or is the honest conclusion "924 data/features do not lift the linear class"?

**This document is committed BEFORE any fit.** Gates and grid are frozen here; the results
section is appended in place afterwards. Every number must be re-derivable from committed
code + the sha256'd inputs below.

## Architecture (fixed)

One lasso head over 924 raw-space features, through the canonical #68 Rust chain
(`bake_dial_refit fit-lasso`: gram-standardize -> lasso-CD (n_sweeps=200, tol=1e-10, tau=0)
-> f16 pack -> dial spline fit on the PACKED forward over the anchor -> canonical serializer),
then `bake_dial_refit add-winsor` (defaults p0.1/p99.9) per B's inclwinsor lineage.

Registered deviations from B's exact lineage (all forced by the 924 regime, stated up front):

- **Single lasso head, no 0.8/0.2 lasso+BVLS ensemble.** The Rust owner has no BVLS solver;
  the campaign question is data/features, not ensemble math. If a single 924 head beats the
  372 ensemble the answer is decisive; if it loses, phase 2 may add BVLS to the owner.
- **No hdr_v3mix leg** (B's cid-head corpus): the 924 set is SDR-only by design; no 924
  extraction of hdr_v3mix exists.
- **No konjnd-dense leg**: DATA_SPLITS' konjnd-train (20,160 rows) exists only at 372/720;
  regime purity bans column-mixing. B also never trained on konjnd data.
- **Raw space** (B's SDR pick lineage `lp_hdrmix-lasso*-raw` was raw-space too); no 924
  Yeo-Johnson transform screen exists. Winsor guards bound the tails instead.
- **Target class**: B's spec says "cvvdp-mix / ssim2-anchored" (ambiguous across its two
  heads). Per protocol we register the human_score-class: each leg's own `human_score`
  column (safesyn = ssim2-derived, cid22t201 = ssim2-anchored — both train-legal), and
  `score_ssim2*` for bigcodec/kadis. No cv/iw mix arm: the canonical 924 legs carry NO
  mix_cv/iw columns (verified: leg schemas are ref_basename + human_score + f0..f923),
  so a mix-target arm is not cheap and is dropped.

## Fit path (owner extensions, no duplication — code in this commit series)

1. `parquet_loader::stream_parquet_rows` — streaming row visitor (same column conventions
   as `load_parquet`, THE loader owner; memory-capped by construction, f64 widening,
   deterministic single-threaded file order; errors on any non-finite feature/target and
   on any null).
2. `bake_dial_refit gram` — per-corpus raw-moment Gram builder: S=Σxxᵀ, s=Σx, q_t=Σx·y_t,
   Y1_t=Σy_t, n (f64, row-sequential accumulation, upper-triangle + mirror) → `.npz`
   (keys `raw__S`, `raw__s`, `raw__n`, `raw__q_<t>`, `raw__Y1_<t>`) via a new minimal
   npz writer in `zensim_validate::npz` (numpy-compatible, CRC32-correct, stored entries).
   Prints rows + input sha256. One gram per corpus; arms combine grams with weights.
3. `bake_dial_refit fit-lasso` extensions: repeatable `--gram` + `--weight` (multi-group
   accumulation `S += w·S_z` exactly as the Python MixGram; single-gram path stays
   bit-identical — parity + byte-repro tests must keep passing), and a parquet anchor
   alternative (`--anchor-parquet` repeatable + `--anchor-target` + `--anchor-scale` +
   `--anchor-stride` + `--anchor-clip-min`) loading through `parquet_loader::load_parquet`.
4. Winsor: `bake_dial_refit add-winsor --fit-corpus ext_safesyn_full.parquet` (defaults
   p0.1/p99.9) on every grid bake — candidates are evaluated in ship form.

**Anchor (dial spline), same for every arm:** stride-sampled rows loaded from the M1 legs
via the owner loader — safesyn stride 139 (799 rows), cid22t201 stride 44 (401), kadid
stride 25 (405), tid stride 7 (429) ≈ 2,034 rows; y = human_score ×100 clipped at −100;
18 knots via the shared `fit_spline_knots`. Fixed across arms so spline provenance never
varies inside the grid.

## Gates (frozen; failure of G-L1/2/3 on every arm = publish "924 does not lift the linear class")

- **G-L1 (primary):** selected candidate CID22 SROCC on the 924 eval (cid22val leg)
  **> 0.8764** (B's number; same 4,292 pairs + MOS, so cross-regime comparable).
- **G-L2:** KonJND abs-SROCC (bake_verdict konjnd leg, per-ref mean PJND) **≥ 0.50**.
- **G-L3:** dial mono **≥ 93%** AND tied **≤ 5%** on the 924 dial grid, AND G-RANGE clean =
  `bake_dial_refit gate` PASS at its default range_frac 1e-4 on ext_cid22val (in-distribution
  preds must sit inside the spline knot domain; the negrich OOD raw range is reported
  alongside, not gated — below-bottom-knot extrapolation on corruption is the designed
  negative-dial path).
- **G-L4 (report-only, NOT a gate):** corruption pass_q20 from the 924 corruption grid;
  expected weak (the corruption head owns that axis).
