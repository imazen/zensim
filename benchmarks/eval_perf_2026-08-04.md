# Eval + trainer performance — 2026-08-04

Data: [`eval_perf_2026-08-04.tsv`](eval_perf_2026-08-04.tsv) (host, commit, command
grid, every number below).

**Headline.** `bake_verdict --regime 944` (the 12-corpus campaign verdict) went
**39.4-40.0 s → 8.8-9.3 s (4.3-4.5×)**; one corpus went **10.39 s → 4.56 s**. A real
wave-7 arm-H training epoch went **14.52 s → 8.16 s (1.78×)** and its validation pass
**11.28 s → 3.24 s (3.48×)**. Every result is **bit-identical** — 82,433 numeric
`--full-json` fields match exactly on the 12-corpus verdict (3 independent run pairs),
10 single-corpus verdicts match exactly, and the trainer's bake bytes are identical
outside the `zentrain.repro` timestamp, with the same `best_val`.

Two new gates make that checkable on any future change:
`scripts/verify_verdict_identity.sh` (whole-JSON, bit-identical by default) and
`scripts/verify_bake_identity.sh` (bake bytes + repro JSON minus provenance keys).

## 1. Where the time actually went (before)

Measured with the new `ZENSIM_PERF_TRACE=1` phase timer
(`zensim_validate::perf_trace`), plus `perf record` for the instruction-level view.

**First finding: `bake_verdict` under-reported its own wall time by ~2×.** It printed
"complete in 34.63 s" for a run that took 39.97 s, because `elapsed` is captured before
the markdown tail and the entire `--full-json` block — including a 4.5 s parquet open —
ran after the timer stopped. The 4.82 s / 35.0 s figures this work started from were
that timer. The binary now prints both (`complete in X (report-timer; Y end-to-end)`).

12-corpus baseline, 39.97 s end-to-end:

| phase | s | share |
|---|--:|--:|
| corpus pre-pass (sha256 of every input) | 1.31 | 3% |
| 12 corpora — parquet load | 7.77 | 19% |
| 12 corpora — MLP forward | 7.84 | 20% |
| 12 corpora — `aggregate_panel` | 11.93 | 30% |
| 12 corpora — bootstrap SROCC CI | 2.31 | 6% |
| 12 corpora — 10-band panel + markdown | 1.27 | 3% |
| DIAL panel (load 0.63 + forward 0.72) | 1.35 | 3% |
| ramp / zone / corruption panels | 0.79 | 2% |
| **`--full-json` KADIS per-pair parquet load** | **4.56** | **11%** |
| json / md / html write | 0.78 | 2% |

So it was ~39% statistics, ~34% parquet IO+decode, ~21% MLP forward — not "the MLP
against a parquet row" being slow. The FLOP estimate in the brief (≈1 GFLOP for CID22
→ "should be ~20 ms") is right about the arithmetic; the arithmetic was never the cost.

`perf` on the CID22 run agreed and added one detail worth recording: **40% of cycles
were in `fmaf` / `compiler_builtins…fmaf_with_fma`**, i.e. `f32::mul_add` inside
`zenpredict::inference::forward` compiling to an out-of-line *software* fused-multiply-add
because the crate is built for baseline x86-64 (no `+fma`). See §5 — that one is in a
sibling repo and was deliberately not touched.

## 2. What changed (all bit-identical, all in `zensim-validate`)

| # | change | why it is identity-preserving |
|---|---|---|
| 1 | **corpora on rayon** (`args.corpora.par_iter()`), results re-assembled in the original order | corpora share nothing until the summary table; 31.2 s of serial work became a 6.5 s max |
| 2 | **`score_grid_one` on rayon** over 512-row chunks, one `Predictor` + scratch per chunk | one row's forward reads only that row; each result is written at its own index — no accumulation order to change |
| 3 | **sha256 pre-pass on rayon** | independent per file; the first error in corpus order is still the one reported |
| 4 | **KADIS per-pair load on a background thread**, joined at its use site | pure scheduling: same file, same `read_cap`, same rows |
| 5 | **bootstrap SROCC CI**: draw all 1000 index sets from the one xorshift stream (still serial — that is what makes it reproducible), then evaluate the `spearman`s on rayon | the RNG stream is untouched; only the independent evaluations move. Generated in 128-replicate blocks so the index buffer stays ~5 MB |
| 6 | **10-band panel on rayon** | the 10 bands are disjoint row subsets, each with its own O(n²) Kendall + PWRC |
| 7 | **`ds_auc` pair sweep on rayon over `i`** | each `i` owns a contiguous pair-index run, so its stride hits are a function of `i` alone; per-`i` outputs are concatenated in ascending `i` |
| 8 | **free the feature matrix right after the forward** (`drop(g)`) | nothing below reads it; cut peak RSS 2.87 → 2.50 GB |
| 9 | **blocked transpose in `parquet_loader`** (1024-row blocks instead of a whole 16 384-row batch) | same values, same order; staging buffer 124 MB → 7.7 MB per open loader |
| 10 | **`ZENSIM_PERF_TRACE=1` phase timer** + honest end-to-end line | diagnostics only |

Threading policy lives in the new `zensim_validate::parallel`: `RAYON_NUM_THREADS` wins
if set (so `run-heavy` stays authoritative), else `ZENSIM_THREADS`, else
`available_parallelism() − 4`. A unit test pins the "leave cores free" rule.

### Trainer

| # | change | why it is identity-preserving |
|---|---|---|
| 11 | **`add_l2_grad_layer1`** — walk `w1` as `n_hidden`-wide rows instead of computing `idx / n_hidden` per weight, hoisting the per-feature multiplier | Rust already evaluates `scale * m * w` as `(scale * m) * w`, so hoisting `sm = scale * m` per row preserves the exact association; the inner `*g += sm * w` is elementwise. ## 3. The trainer finding worth keeping

A `perf` profile of a **live** SOTA-944 training run (read-only sampling of the running
process — no extra load) split as:

| symbol | share |
|---|--:|
| `mlp_train::train_mlp_strategy` (self) | 46.1% |
| `adam_simd::__arcane_adam_update_inner_v4` (AVX-512) | 26.5% |
| `simd_mlp::forward_avx512` | 14.8% |
| `simd_mlp::backprop_avx512` | 6.4% |
| `zenstats::panel::sa_st_curve` (validation PWRC) | 3.9% |
| `mlp_train::apply_coarse_decay` | 1.5% |

Annotating that 46% self-time put **93.6% of it — ≈43% of all trainer cycles — on five
instructions**: a scalar `div` + `mulsd` + `addsd`-to-memory + store, i.e. the layer-1
L2 gradient loop

```rust
for (idx, (g, &w)) in adam.gw1.iter_mut().zip(w1.iter()).enumerate() {
    let m = fmult.as_ref().map_or(1.0, |v| v[idx / n_hidden]);   // 32-bit DIV per weight
    *g += hyperparams.l2_lambda * m * w;
}
```

At 944 × 128 weights applied once per pair, that is ~6 × 10⁹ integer divisions per
50 000-pair epoch. Removing them (change 11) is the whole 1.78× on the training step.

**The trap that put it there.** `--coarse-decay` alone — no `--coarse-l2-mult` — sets
`L2_FEATURE_MULT = Some(2.0 on the coarse rows)` purely so the *decoupled* decay gate
`m > 1` engages. As a side effect it switches this loop from the `None` fast path onto
the divide path. Every campaign recipe that passes `--coarse-decay` (all of the
coherence-era and wave-5/6/7 arms) paid for it, while the coupled multiplier it enables
is documented two functions up as "neutralized by Adam". The comment on
`add_l2_grad_layer1` records this so it is not rediscovered.

**Correction to the brief's premise.** The brief expected validation to cost ~2.4× the
training step. Measured, it is **7.2% of a 10-epoch window** before this change and
**2.2%** after: `--log-every` (default 10) already gates the validation panel to one
epoch in ten, so no new `--val-every` / `--val-fast` flag was added — the knob exists,
it is `--log-every`, and it is already at a sane default. Validation was still worth
parallelizing (3.48×, free, bit-identical), but it was never the bottleneck.

## 4. Fixed cost vs per-row cost

Per the sweep discipline, fitted `total = α + β·rows` over the 10 single-corpus runs:

| | α (fixed) | β (per row) | R² |
|---|--:|--:|--:|
| baseline | 7.018 s | 0.5930 ms/row | 0.986 |
| optimized | 3.921 s | 0.2048 ms/row | 0.884 |

α dominates every corpus below ~10 k rows and is **not** the corpus's own work: it is
the bake load, the sha256 pre-pass, the dial grid, the corruption grid, the KADIS
per-pair read, and the report write — all of which a `--corpora cid22` run pays in
full. That is why a 50-row corpus (SDR25) and a 4292-row one (CID22) both cost ~4.2 s
after this work: **they are both ~100% intercept.** Anyone benchmarking "ms/row" on
this binary without the intercept will get a number that is wrong by 50-100× at the
small end.

The optimized R² is lower because the slope is no longer one line: corpora with the
10-band panel enabled (CID22/KADID/TID) carry ~10 extra O(n²) panels, so at n≈10 k
KADID costs 6.26 s against imazen26's 5.48 s at the same size.

Most of α is IO on the 9p `/mnt/v` mount (`cache=0x5`, `msize=65536` — every read is a
64 KB round trip). A 12-corpus run reads ~1.3 GB; the CID22-only run reads ~600 MB, of
which the KADIS per-pair window is ~490 MB. That read is now overlapped, not removed.

## Memory

Peak RSS on the 12-corpus verdict rises **728 MB → ~2.48 GB**: twelve corpora and the
KADIS window are in flight at once instead of one at a time. It is bounded and
tunable — `ZENSIM_THREADS=8` gives 10.52 s at 2.16 GB, `=4` gives 15.71 s at 1.86 GB,
and `MALLOC_ARENA_MAX=2` trades 9% time for 18% RSS. The knee is at 8-16 threads; the
default (24) buys the last 12%. Single-corpus runs go 728 MB → 951 MB.

## 5. Deliberately NOT done

> **DONE 2026-08-04 (same day).** The first two items below were sibling-repo work
> that this pass could not do; the user then authorized cross-repo edits and both
> shipped. Numbers, profiles and the identity gate:
> [`fma_zenstats_perf_2026-08-04.tsv`](fma_zenstats_perf_2026-08-04.tsv). Commits:
> zenanalyze `05de3cbc` (FMA dispatch), zenmetrics `29f1d61e` (parallel sweeps);
> zensim consumes both by git rev — nothing was published. Combined, the 12-corpus
> verdict went **8.98 s → 6.87 s (1.31×)** and its CPU time **29.97 s → 21.51 s
> (1.39×)**, still bit-identical on all 82 433 numeric fields.

- ~~**`zenpredict::inference::forward`'s software FMA.**~~ **DONE — and the estimate
  below was 10× too conservative.** A default-on `simd` feature puts archmage
  `#[autoversion(v3)]` on the three `saxpy_matmul_*` kernels, recompiling the
  *unmodified* bodies under `+avx2,+fma`. The guessed "2-3×" assumed the cost was
  just call overhead; in fact a call per element blocked vectorization outright, so
  removing it also unlocked 8-wide SIMD. Measured on the shipped 944→128→1 shape
  (zenbench): **210.9 µs → 8.27 µs, 25.5×**, 573 M → 14.6 G FMA/s. `fmaf` is now
  absent from the profile and the whole forward is 4.02% of cycles, down from ~53%.
  Semantics are unchanged by construction — `f32::mul_add` and `vfmadd` are both
  IEEE-754 `fusedMultiplyAdd`, and the SAXPY loop accumulates each lane into its own
  `dst[k]`, so widening it reassociates nothing.
- ~~**`zenstats`' O(n²) `kendall_tau` and `sa_st_curve`.**~~ **`sa_st_curve`
  parallelized; `kendall_tau` parallelized but NOT converted to Knight's — see
  below.** This section's "~30%" bundled the two; measured separately on the
  post-FMA binary, `sa_st_curve` is **18.3%** of cycles and `kendall_tau` never
  exceeds 1.65%. Parallelizing both (exact: `i64` counters and an f64 `max`, so the
  reduction cannot round) gave 6.28 s → 4.95 s on the largest single corpus.
  - **Knight's O(n log n) `kendall_tau` is not applicable here, and that is a
    finding worth keeping.** The tie predicate is approximate (`|Δ| < 1e-12`),
    which is **not transitive** — `a = [0, 0.9e-12, 1.8e-12]` has 0~1 and 1~2 tied
    but 0~2 not — so no sort-based τ-b can represent it: on `b = [1, 2, 3]` zenstats
    returns 0.5774 where scipy returns 1.0. A Knight's port would have passed the
    obvious gate (exhaustive permutations of *distinct* values, *exactly*-tied
    fixtures — neither exercises chained near-ties) and silently moved KROCC.
    `kendall_epsilon_ties_are_not_transitive` in zenstats pins it.

### Still not done

- **A batched GEMM forward inside `zensim-validate`** — unchanged from below; the
  25.5× came from the owning crate instead, which is where it belonged.
- **Enabling `simd` for `zenpicker`.** It takes zenpredict with *no* features for
  `no_std` codec embedding, and `simd` implies `std`. That is a portability
  decision for whoever owns codec embedding, not a perf patch. (`zenpredict-bake`
  and `zenpicker-train`, both host-side, were switched on — they had
  `default-features = false` and would otherwise have silently missed the dispatch.)
- **A batched GEMM forward inside `zensim-validate`.** It would duplicate
  `zenpredict`'s forward (banned by the no-duplicate-implementations rule) and would
  have to reproduce every head + spline path bit-exactly. Per-row parallelism gets the
  same wall-clock win with none of that risk.
- **A `--val-fast` / `--val-every` trainer flag.** `--log-every` already is it (§3).
- **Changing `--minibatch-size`.** The campaign recipes run K=1, which makes the
  training step serial by construction. K>1 changes the Adam cadence and therefore the
  result — it is a recipe decision, not an optimization.
- **Global `RUSTFLAGS=-C target-feature=+fma`.** It would fix the software-FMA problem
  for the whole tree bit-identically, but it raises the ISA floor of every binary built
  from this workspace, including the published `zensim` library. That is a release
  decision, not a perf patch.

## 6. Reproducing

```sh
# eval, before/after on any bake
ZENSIM_PERF_TRACE=1 bake_verdict --bake <bake> --regime 944 --name p \
    --full-json a.json --output a.md
scripts/verify_verdict_identity.sh a.json b.json      # must print PASS

# trainer: run BOTH binaries from the same path AND the same --out path,
# moving the output between runs (argv is embedded verbatim in zentrain.repro)
scripts/verify_bake_identity.sh base.bin opt.bin      # must print PASS
```
