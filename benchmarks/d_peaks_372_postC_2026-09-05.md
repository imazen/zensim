## 2. ⛔ `extract_features_372col` DOES NOT EMIT ROWS IN INPUT ORDER

**Read this before re-attaching any key column to its output.** The binary ends
with

```rust
rows.sort_by(|a, b| a.0.cmp(&b.0));   // extract_features_372col.rs:216
```

— a stable sort on `ref_basename`. Groups come out alphabetically by reference.

**It fails silently.** The row count is right, every key appears exactly once,
and only the pairing is scrambled. The first build of the 2026-09-05 dial grid
attached `(image_id, codec, q)` positionally and shuffled features across the 38
references. What that produced:

* every scorer's ladder monotonicity collapsed — shipped D **0.9847 → 0.5611**,
  Profile A 0.9782 → 0.5827, shipped B 0.9792 → 0.5662;
* jpeg q0 read a dial of **75.6** on an image whose ssim2 truth is −8.03;
* `peer_ssim2`'s `tied` read **0.0672** where the registry says 0.0000 — which
  is what caught it, because a *reference* metric's own value moving on an
  instrument that is supposed to be the same cells is not a candidate's problem.

Nothing errored, and three of the five G-ADDR grid scalars were unchanged.

**The fix does not touch the extractor** — other callers' positional comparisons
against stored tables depend on that sort, and the root build above is one of
them (both sides sorted identically, which is why its `human_score` gate passes
bit-exactly). `scripts/canonical_corpus/build_dial372_instruments.py` writes a
numeric `row_id` into the pairs TSV, `load_pairs_tsv` forwards every numeric
extra column, and the permutation is inverted and **checked** (out-of-range,
duplicate, or missing `row_id` all refuse).

Post-fix: the identity and negative-tail probes are byte-identical to their
pre-fix builds (their pairs lists happened to be sorted by reference already —
verified, not assumed), and only the two grids moved.

gain, AND no contract row lost."* Both hold: CID22 **+0.00798** with a CI

* **It is not a rank sweep.** TID **−0.01853** [−0.02202, −0.01539] and AIC-3

## 6. `--feature-set-id` — the stamp, and why it is caller-supplied

`bake_dial_refit fit-lasso --feature-set-id <id>` writes
`zentrain.feature_set_id` through the canonical
`zenpredict_bake::append_metadata_utf8`. The stamp names the **producer** — the
tables the fit trained on — which is the semantics
`feature_set::bake_declared_training_set` already documents.

The ERA cannot be derived here (a gram has no provenance; §4.3 had to *measure*
it), so it is supplied. Everything else is CHECKED against the bytes just
emitted: the id must parse, be registered, be role `producer`, match the bake's
caller width, and its slot set must COVER every line the bake reads. A
disagreeing stamp is **refused, not written** — a stored id is what
`bake_verdict` treats as ASSERTED rather than inferred, so a wrong one is worse
than none.

Default OFF. The byte-repro control passes: `fit-lasso` without the flag still
reproduces `51437a34f04887ce850b25eff4f72a6bcd12926873ce060a12878d558a7517db`
(`--expect-sha256`), and the stamped peaks bake with `repro` +
`feature_set_id` stripped is byte-identical to the unstamped one
(`f6c0da28261c82f9…`).

Gate: `tests::feature_set_id_stamp_is_checked_against_the_bake_bytes` — four
refusals (a bare count, an unregistered era, a consumer-role entry, a w944
producer on a w372 bake), an assertion that every refusal leaves the file
untouched, and one accept that reads back through the owner.

Visible effect: `bake_verdict` now reports the train/serve era skew for this
bake explicitly —

```
feature-set — table basic+peaks+masked+iw@w372/v1postc#d16a1091
feature-set — bake  basic+peaks@w372/v1pre#a071348e
feature-set MISMATCH — EraDiffers: bake trained on era v1pre, table is era v1postc
```

## 7. A resolution defect this uncovered: a DECLARED `feature_set_id` resolved to
NO slots

`feature_set::root_feature_set_ref` looked a manifest-declared id up with
`reg.set(&id.to_string())` — the FULL id including `#hash8` — while every
registry key is the CLASS form with the hash in the value. So the branch the
design calls *most authoritative* always fell through to an **empty slot set**,
and `check` then reported every slot the consumer reads as `SlotsNotPopulated`.
The 2026-09-05 root is the first artifact to carry the key, and it immediately
produced **28 spurious "not populated" slots** for a 372-input bake against a
372-wide root that populates all 372.

Fixed by falling back to the class form **only when the registered
`slots_hash8` agrees with the declared one** — a disagreement means the name and
the bytes have come apart and must not resolve silently. Gate:
`a_manifest_declared_feature_set_id_resolves_to_the_registered_slots`, which
writes its own manifest (needs nothing from block storage), carries the
hash-disagreement negative control, and was verified to FAIL before the fix
(`left: SlotSet { ranges: [] }`).
