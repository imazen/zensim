# V0_20 + V0_21 design — bake-time input shaping + linear distillation

Status: design + scoping, 2026-05-14. Concrete experiments queued
behind V0_19 ship (no point training input-shaping or distillation
variants against a contaminated teacher).

---

## V0_20 — algorithmic input shaping

### Premise

zenpredict 0.2.0 already supports per-feature `FeatureTransform`
metadata (Identity / Log / Log1p). The trainer can emit
`feature_transforms` in the bake metadata; the runtime applies them
inline via `Predictor::predict_transformed`. Today every shipped
V_X bake ships with all-Identity transforms — we've never actually
used the mechanism.

V0_20's goal: extend `FeatureTransform`, then **train, validate, and
compare** V_X bakes that use the new variants per-feature. The MLP
gets to see features in a shape that linearizes the relationship
between feature value and target score; we expect SROCC + per-band
calibration to improve at constant model size.

### Variants to add to `FeatureTransform`

The existing wire format reserves bytes 0..255 for transform tokens.
Adding new variants is back-compatible: old runtimes that don't know
a token return `UnknownFeatureTransform` and fall back to Identity
(or refuse to load, depending on consumer policy — opt-in strict mode
should be on for codec runtimes shipping the bake).

Proposed additions:

| Token | Math | Use case |
|---|---|---|
| `signed_log1p` | `sign(x) · ln(1 + |x|)` | Bidirectional log: useful for centered-zero features (sign-balance, residuals) |
| `sqrt` | `sign(x) · sqrt(|x|)` | Variance-stabilizing, milder than log; good for moderate skew |
| `cbrt` | `sign(x) · cbrt(|x|)` | Even milder; preserves direction with reduced tail |
| `clip_then_log1p` | `ln(1 + max(0, x − ε))` | Feature has known floor `ε`; subtract then log1p |
| `winsor_p99` | clip to `[p1, p99]` of training distribution | Robust to outliers; trainer ships the (p1, p99) per feature in metadata |
| `quantile_bins` | bucket x into N quantile bins, emit bin index / N | Strict monotone transformation, captures non-linear feature/score relationship without changing model topology |

`winsor_p99` and `quantile_bins` require per-feature scalar parameters.
We extend the bake metadata schema:

```
zentrain.feature_transform_params : map<u32, [f32]>
  feature_idx → variable-length f32 params
```

Layout encodes which feature uses which transform separately (the
existing `feature_transforms` u8 array) and the params for the
parameterized variants in a parallel section. Loader cross-references
on read.

### Methodology

For each candidate transform variant + each feature:
1. Fit the transform (Identity is baseline, parameterized variants
   need their parameters fitted from the training-side feature
   distribution).
2. Build a `feature_transforms` config that applies the transform
   ONLY to that feature (all others stay Identity).
3. Train a V0_16-base-equivalent MLP with the same recipe used for
   V0_19 base (single MLP, h=128, seed=1, no TV).
4. Evaluate on the 10-band primary grid (CID22 + KADID + TID +
   AIC-3 + KonJND).
5. If a transform clears `Δ_aggregate_SROCC ≥ +0.001` AND no per-band
   regression > 0.01 SROCC, mark it as a winner for that feature.

Then a second pass: greedily compose the winners across features
(per-feature transforms are additive — different features can use
different transforms with no shared parameters). Re-train. Validate.

### Estimated compute

7 new transforms × 228 features ≈ 1600 single-feature training runs.
Each ~24 min on this box ≈ 640 hours. **Too expensive in series.**

Mitigation: greedy feature selection on TRAIN-SIDE per-feature
correlation analysis first (Pearson rank corr of f_i vs human_score
before/after transform), then only train MLP variants for features
where the correlation gap > 0.01. That filters ~1600 candidates down
to maybe 50-200. ~20-80 hours.

Further mitigation: train ONLY the changed-feature columns of the
MLP via warm-starting from V0_19 weights — incremental fine-tune is
~5 min per variant instead of 24. Total ~10-20 hours for the full
sweep.

### Ship gate

V0_20 ships if the post-shaping aggregate CID22 SROCC beats V0_19 by
≥0.002 AND no per-band SROCC regressing more than 0.005. Bin shrink
on 10-band low-q (B2..B5) is the most likely target — those bins
typically have the noisiest f_i ↔ score relationships.

## V0_21 — linear distillation from best MLP

### Premise

V0_2 is a pure linear `dot(features, weights) / num_scales` — 228
weights, no hidden layer, no activation. Sweep-time computation is
~1 µs per pair. V0_2 aggregate CID22 SROCC is 0.8676 (vs V0_18's
0.8933).

V0_21's question: can we extract a NEW pure-linear weight set that
matches V0_18's SROCC (or at least exceeds V0_2's) without an MLP at
runtime? If yes, we ship a tiny ~1 KB bake that codec hot loops can
compute almost free.

The naive "average V0_18's first-layer weights into a linear vector"
doesn't work because the LeakyReLU between layers means the MLP's
forward pass isn't a linear function of inputs. We need to learn the
linear approximation that best matches V0_18's predict outputs.

### Approach

1. **Generate the distillation set.** Run V0_18 on each row of the
   full training corpus (synth-v2-purged ∪ KADID-features ∪
   TID-features ∪ KonJND-features). Collect 1M+ (features, V0_18_score)
   tuples.
2. **Optional feature engineering.** The MLP's nonlinearity comes
   partly from feature interactions. A pure-linear model on RAW
   features can't capture those; but a linear model on **engineered**
   features (polynomial, product, ratio) can approximate well.
   Candidate engineered features:
   - Original 228 features
   - Pairwise products f_i · f_j for the top-50 most-important features
     (importance = MLP's gradient × input magnitude)
   - Quadratic terms f_i^2 for all 228
   - Log/sqrt transforms (subset)
3. **Fit ridge regression.** L2-regularized linear regression on
   `(engineered_features, V0_18_score)`. Tune `α` via 5-fold CV on
   held-out synth-v2 rows.
4. **Wire format.** A pure-linear distillation can ship as a single-layer
   bake: 228 (or N engineered) → 1 with no hidden, no activation. The
   existing ZNPR v3 format already supports this — `n_layers = 1`,
   `out_dim = 1`, `activation = Identity`. ~1 KB binary.
5. **Validate.** 10-band SROCC against human MOS, compare against V0_2
   AND V0_18.

### Ship gate

V0_21 ships if CID22 SROCC ≥ V0_2's 0.8676 + 0.005 (i.e. ≥0.8726).
The full goal is to beat V0_2 by enough margin to be a meaningful
"fast scorer" option in the public API, while staying under V0_18's
binary cost by ~100×.

### Inference cost target

V0_2 inference: ~228 multiplies. V0_18 inference: ~88k multiplies
(228×384 + 384). V0_21 with engineered features: depends — pure
228 features = 228 multiplies (same as V0_2). With 50 pairwise
products = 278 multiplies (+22%). With full pairwise = ~26k multiplies
(slower than V0_2 but still 3× faster than V0_18).

The tradeoff is binary size and inference cost vs SROCC margin over
V0_2. Pick the smallest engineered set that gets within 0.01 of V0_18
on CID22.

→ V0_21 ship.
